## D. 정책 문서 4종 (핵심 문장만)

### D.1 admission-policy
```text
- 후보자는 승인 전 SOUL을 스테이킹하지 않는다 (맨손 신청).
- 검증 + Persona Profile + Application Statement + (선택) Persona Clip 후 CandidateApplication 제출.
- Persona Clip 미제출은 거절 사유가 아니다. KYC/liveness/unique-human 대체 아님. 자동 점수 아님.
- 입장심사는 기존 멤버의 stake-backed review로 발전하도록 설계.
- Support/Challenge는 의견이 아니라 장기적으로 ReviewPosition + Review Toll/Bond를 수반하는 보증 행위.
```

### D.2 reviewer-guideline
```text
- Persona Clip 유무로 평가 금지. 미제출은 거절 사유 아님. tone/presence 참고자료일 뿐.
- 외모/억양/말투/계층신호/영상퀄리티 과의존 금지.
- Support는 좋아요가 아니라 내 Staked SOUL로 입장을 보증하는 행위.
- Challenge는 비추가 아니라 근거 있는 위험신호. 악성/파벌성/외모기반 Challenge는 장기적으로 bond/slash 대상.
```

### D.3 membership-policy
```text
- 승인 시 membership row + active.
- 장기적으로 승인자는 Activation SOUL 수령 가능 → 즉시 DefaultStakedSoul로 lock.
- Activation SOUL ≠ 보상/에어드랍/수익/양도토큰. 신규 발행 없음. Review Toll/준비금에서만.
```

### D.4 (신규) persona-clip-policy 또는 admission-policy 내 절
```text
- 선택 제출. 앱내 녹화 only. 업로드/미리보기/재촬영/편집/필터/자막/AI분석/점수화/추천/공개피드/영상메시지 없음.
- 권한거부·녹화실패 시 clip 없이 계속 진행.
- 심사 참고자료. 필수 검증수단·자동 점수 요소 아님.
- ★ 보존: terminal admission state(approved/rejected/withdrawn) 도달 즉시 raw media 삭제.
  draft 24h 미제출 clip도 삭제. 영구 보존 금지. (가입절차 끝나면 raw clip 안 남김 — INV-PC-09)
```

## E. ⚠️ Claude가 보는 잔여 설계 충돌 / 주의점

1. **persona_clip_assets vs evidence_files 중복 우려.** 둘 다 storage_provider/content_hash/migration 필드를 가진다. 별도 테이블로 두되(권한·보존정책이 다름), StoragePort는 공유하는 게 깔끔. Task 3에서 두 테이블이 컬럼을 베끼지 않게 주의.

2. **Persona Clip 보존정책 — 확정됨(v1.3).** terminal admission state 도달 즉시 raw media 삭제 + draft 24h 미제출 삭제 + 영구보존 금지. 상태전이 rpc가 delete_after를 찍고 삭제 워커가 Storage 객체 제거. persona_clip_hash(해시)만 남고 raw media는 안 남는다. "검열저항·data minimization" Northstar와 정합. (INV-PC-09, BuildPlan §5.2.2)

3. **녹화 자체가 INV-PC-06과 긴장.** 클립 원본은 private storage엔 있어야 재생이 되지만, audit/outbox/log엔 0건이어야 한다. "저장은 하되 흔적은 안 남긴다"의 경계를 Task 7에서 명확히. 로그에 storage_path는 OK, 바이트/transcript는 금지.

4. **Admission Underwriting을 schema로만 두는 것의 위험.** Review Toll/Bond/Activation 경제를 P0에서 구현 안 하는 건 맞다. 다만 reviewer가 P0에서 "그냥 승인 버튼"만 누르면, 나중에 stake-backed로 바꿀 때 reviewer 멘탈모델이 굳어버린다. reviewer-guideline에 "지금은 버튼이지만 곧 네 stake가 걸린다"를 명시(이미 D.2에 반영)하고, ReviewPosition 테이블을 stub으로라도 §5에 둬서 자리를 비워둘 것.

5. **chain-neutral의 부작용 — `external`이 모호.** 지금은 의도된 모호함(다음 라운드에 결정)이지만, Task 10 전까지 누구도 `LedgerChain="external"`을 실제 처리하면 안 된다. OutboxProcessor 메인 분기는 여전히 internal only, external_ledger는 dead_letter. (기존 §7.5 규칙 그대로, 이름만 바뀜.)
